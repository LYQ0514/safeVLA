可以继续，但先把它定位为“真实危险正对照 smoke”，不要直接称为完整评测。`task2 ep16` 可以作为候选，但必须先通过因果筛选。

- ep44 的 `n_repairs=0` 对当前 robot-obstacle 安全事件确实是正确行为。它是场景稳定性反例，不是 PNSG 负例。

## 先冻结真实碰撞筛选门

候选 episode 必须同时满足：

1. 第一次禁止接触明确为：

```text
robot_geom ↔ obstacle_geom
```

或抓取阶段允许纳入：

```text
target_geom ↔ obstacle_geom
```

2. 同一 pre-contact snapshot、相同暴露窗口下：

```text
nominal branch：出现禁止接触
hold/zero-action branch：不出现该接触
```

3. 初始状态不存在相同 geom pair 的穿透或持续接触。

4. 碰撞前最后一次决策的实际执行动作落在认证前缀内。若 `execute_steps=2`，应能指出碰撞由 chunk 的第 0 或第 1 个动作触发。

5. 状态恢复一致性通过。

6. 对“PNSG steering 正对照”，还要求代理确实检测到风险：

```text
S_fast 或 S_wide = FAIL
C_2(nominal) = FAIL
```

如果 `C_2=FAIL` 但代理仍显示安全，那测到的是 proxy miss，不是 source repair 效果。

在筛选出的 pre-contact 状态固定：

```text

| 组别 | 候选 |

| Pα | \(\alpha\in\{0.25,0.5,0.75,1\}\) |

每个候选记录：

只有下面这个结果才算 source steering 的强正对照：

PNSG:      progress 不劣于 nominal，或至少没有明显退化

```

## 完成两步正对照后，再跑闭环

如果上述门通过，再从同一 snapshot 开始做滚动闭环：

```text
每次重新获取观测
→ 固定方式生成 z0
→ nominal certification
→ 必要时 source repair
→ 执行 2 步
→ 重复至成功、失败或固定上限
```

报告：

- 实际 repair 次数；
- nominal 被拦截次数；
- repair 后认证通过率；
- robot-obstacle contact；
- target-obstacle contact；
- 任务成功；
- 总步数；
- 进度损失；
- 计算开销。

这个闭环结果仍是案例验证，不是总体性能估计。

## 场景物理稳定性应成为前置门

以后每个正式场景先做短期稳定性检查：

```text
SCENE_STABILITY_GATE
```

至少记录：

- 初始 penetration；
- hold/zero-action 下的 obstacle displacement；
- obstacle–environment contact；
- 是否出现无机器人因果接触的大位移。

不稳定状态标记：

```text
SCENE_PHYSICS_UNSTABLE
```

这类状态可以保留在原始数据和敏感性分析中，但不能用来判断 PNSG 是否避免了机器人碰撞。

CAR 建议拆成：

```text
robot_obstacle_contact_rate
target_obstacle_contact_rate
causal_obstacle_displacement
scene_instability_rate
```

不要再用单一“障碍物是否移动”同时代表四种机制。
