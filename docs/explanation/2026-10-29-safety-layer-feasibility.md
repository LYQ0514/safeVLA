# 安全约束层可行性评估（AEGIS CBF-QP 方案）

- **日期**：2026-10-29
- **类型**：技术可行性评估 / 设计决策
- **结论**：**核心算法可用，官方代码不可直接用**。建议采用「oracle 感知 + CBF-QP」路线。

---

## 一、结论摘要

| 项 | 结论 |
|---|---|
| CBF-QP 数学 | ✅ **验证可用**（已独立实现测试） |
| QP 实时性 | ✅ **中位 0.51 ms**，远低于 20Hz 的 50ms 预算 |
| 障碍物几何获取 | ✅ **可直接从 MuJoCo 取**，无需深度相机 |
| AEGIS 官方代码 | ❌ **无法在公开版 SafeLIBERO 上运行**（见第三节） |
| 感知链路（GroundingDINO + 云端 VLM） | ❌ **不建议复现**（有硬阻塞，且是精度瓶颈） |
| 建议路线 | **oracle 感知 + 自研 CBF-QP** |

## 二、已验证可行的部分

### 2.1 CBF-QP 数学（实测）

用 AEGIS 的 `compute_h_coeffs_3d` + `cvxpy.OSQP` 独立构造测试：
末端椭球 p1、障碍椭球 p2，参考速度**直冲障碍**，观察 QP 如何修正。

| 距离 | h 值 | QP 是否介入 | 输出速度 |
|---|---|---|---|
| 0.60 m | +0.490 | 否 | `[1.0, 0, 0]`（原样放行）|
| 0.30 m | +0.190 | 否 | `[1.0, 0, 0]` |
| 0.20 m | +0.090 | **是** | `[0.9, 0, 0]`（轻微减速）|
| 0.15 m | +0.040 | **是** | `[0.4, 0, 0]`（明显减速）|
| 0.10 m | -0.010 | **是** | `[-0.1, 0, 0]`（停止并后退）|
| 0.05 m | -0.060 | **是** | `[-0.6, 0, 0]`（强力后退）|

**行为完全符合 CBF 预期**：远离时不干预（不损失任务性能），靠近时平滑减速，
进入危险区（h<0）时反向推开。这正是"仅在必要时干预"的设计意图。

### 2.2 求解速度（实测 200 次）

```
中位 0.51 ms | 95% 0.87 ms | 最大 43 ms（首次预热）
```

20Hz 控制下每步预算 50ms，**QP 只占 1~2%**。实时性无问题。

### 2.3 障碍物几何：可绕过整条感知链路

我们**有仿真特权信息**，不需要深度相机 + 检测模型：

| 需要的东西 | AEGIS 的获取方式 | 我们的方式（更准） |
|---|---|---|
| 障碍物位姿 | GroundingDINO 检测 + 深度点云反投影 | `obs["<name>_pos"]` / `obs["<name>_quat"]` |
| 障碍物形状 | 最小体积包围椭球拟合点云 | MuJoCo `geom_size` 直接读（17 个 geom 取最大半轴）|
| 障碍物身份 | **智谱 GLM-4.5v 云端 API** | `sim.model.joint_names` 里筛 `obstacle` |

实测 moka pot 障碍物的包围半轴：`[0.0634, 0.098, 0.1173]` 米 —— 精确、免费、无网络。

**这不是偷懒**：VLPSA（arXiv 2609.22462）重评 VLSA 时明确采用了同一做法
（"we replace online vision language model (VLM) obstacle identification with
ground-truth labels"）。**用 oracle 感知隔离控制层贡献，是已被采用的标准协议。**

## 三、官方代码不可直接用的三个硬阻塞

### 阻塞 1：`eef_marker` body 不存在（会直接崩）

AEGIS `main_aegis.py` 第 ~138 行：

```python
eef_body_id = model.body_name2id("eef_marker")
```

而**公开版 SafeLIBERO 没有这个 body**，实测直接抛：
```
ValueError: No "body" with name eef_marker exists.
```

**为什么**：AEGIS 仓库里的 `safelibero/libero/libero/assets/scenes/libero_tabletop_base_style.xml`
比 HuggingFace 公开版**多了一行** `<body name="eef_marker" pos="0 0 1.3">`。

> ⚠️ **这本身是个值得记录的复现性问题**：AEGIS 报告的数字来自一个**与公开基准略有差异**的环境。
> 差异虽小（我们确认 eef_marker 只用于可视化，CBF 实际用 Python 变量 `p1`），
> 但说明"用官方仓库跑出论文数字"这件事并不成立。

**对我们**：这行是纯可视化用途，**直接删掉即可**，不影响算法。

### 阻塞 2：障碍物识别依赖云端 VLM，且 API key 为空

`utils.py::obstacle_detection()`：

```python
api_key = ""
if api_key is None or api_key == "":
    raise ValueError("Please enter api_key")
client = ZhipuAiClient(api_key=api_key)
model="glm-4.5v"
```

即**每个 episode 开头要调用一次智谱 GLM-4.5v 云端多模态 API**，每步还要 GroundingDINO 推理。

**这是硬阻塞**：需要付费 API key + 外网。我们不该为了复现引入外部付费依赖。

### 阻塞 3：重型感知依赖

`groundingdino-py==0.4.0`（+ ~700MB 权重）、`open3d==0.19.0`、`zai-sdk`、`supervision`，
且要求 `torch==1.11.0+cu113` —— 与我们的 `.venv`（3.8 + 无 torch 冲突处理）不兼容。

## 四、AEGIS 实现本身的可改进点

即使抛开感知，其 CBF 实现也有几处我们可以做得更好：

| 问题 | 说明 | 我们的改进 |
|---|---|---|
| **障碍椭球只在 episode 开始时拟合一次** | 之后不再更新。障碍物被碰动后椭球就错了 | 每步更新（VLPSA 也批评了这点）|
| **QP 不可行时回退到原始动作** | `if u.value is None: 用 action` —— **安全层失效时反而执行最危险的动作** | 回退到"急停"或上一安全解 |
| **只约束单一障碍物** | 只取工作空间内第一个 obstacle | 支持多障碍物约束 |
| **改 `model.body_pos` 做可视化** | 在 episode 中修改静态模型 | 不改模型，可视化另算 |
| **感知失败静默关闭安全层** | 点云为空 → `flag_safety_control=False` → 退化为无安全层 | 显式记录并报告降级 |

**最后一个尤其重要**：AEGIS 论文里 CAR 只有 77.85% 而非 100%，
作者自己归因于"上游感知局限"。我们的 oracle 方案可以**把感知误差这一项完全消除**，
从而验证控制层本身的真实上限。

## 五、建议路线

### 方案 A（推荐）：oracle 感知 + 自研 CBF-QP

```
π0.5 策略（子进程 py3.11）
        ↓ action (7维)
[CBF-QP 安全层]  ← py3.8，cvxpy
   输入：obs（eef 位姿、障碍物位姿、geom 尺寸）
   输出：修正后 action
        ↓
env.step()
```

**工作量**：核心约 **300~400 行**，估计 1~2 天。

- 复用已验证的 `compute_h_coeffs_3d` 数学（MIT/学术使用，注明出处）
- 感知用 oracle，安装成本为零
- 直接接入现有 1600 条评测框架，可与基线严格对比
- 可做消融：单障碍 vs 多障碍、静态椭球 vs 每步更新、可行性回退策略

**预期收益**：AEGIS 报告 CAR 18.7% → 77.9%。我们在 oracle 感知下应能超过它，
因为消除了感知误差这一主要残余来源。

### 方案 B：完整复现 AEGIS

需要：智谱 API key（付费）、GroundingDINO 权重重下、独立 torch 1.11 环境、
给所有场景 XML 补 `eef_marker`。

**不推荐**：成本高、依赖外部付费服务，且复现出的数字仍无法与论文严格对齐
（环境已确认有差异）。**仅在需要"严格对比同一实现"时才值得**。

### 方案 C：更简单的安全基线

如速度限幅、势场排斥。可作为**下界对照**（证明 CBF 这种"有理论保证"的方法确实更好），
工作量约半天。

**建议**：先做 A，把 C 当成消融里的一个对照项（很便宜）。

## 六、待确认

1. **是否接受 oracle 感知**？这决定了能否绕开付费 API。学术上已有先例（VLPSA），
   但若目标是"真实部署"，则感知链路必须解决。
2. **安全层放在哪一层**：
   - 当前位置级（改 action）—— 简单，但只保护末端点
   - 全身级（像 VLPSA 那样保护整臂 + 持物）—— 更完整，但几何建模复杂得多
   建议先做末端级，验证有效后再考虑全身。
3. **是否要做方案 C 作为对照**（约半天，能让论文里的对比更完整）。
