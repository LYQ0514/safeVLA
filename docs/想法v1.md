这个现象非常重要，但“根因是单 chunk 看不到跨 chunk 碰撞”目前下得过早。更准确的结论是：

> 端到端链路虽然跑通，但当前安全代理/认证/执行链没有在碰撞前触发干预。真正失效的位置尚未定位。

## 一个关键时间逻辑

如果你的配置是 `execute_steps=2`，15 次决策执行 30 步，那么 step 19 大约属于第 10 次决策实际执行的两步。

在该决策点，\(H=10\) 的 nominal chunk 理论上覆盖 step 18–27。因此 step 19 并不在预测视野之外。

即使每次执行完整 10 步，step 19 也应位于第二次决策生成的 chunk 内。你目前展示的是某一次 chunk 的净空序列，尚不足以证明“每次滚动预测都安全”。

所以当前不能归因于 horizon，除非你能证明：

1. 碰撞前最后一次重规划的 chunk 没有覆盖碰撞动作；或
2. 运行时确实没有在碰撞前重新规划。

## 更可能的四类原因

### 1. 抓取物体—障碍碰撞漏建模

你当前代理只有“91 个机器人控制点球 + 障碍球”。如果 first contact pair 是：

```text
被抓取物体 ↔ yellow_book
```

那么代理给出 177–242 mm 的机器人净空完全可能是正确的，但遗漏了真正的碰撞主体。

这是第一优先排查项。请记录第一次接触的：

```text
geom1
geom2
body1
body2
contact.dist
contact position
```

如果是 target–obstacle，根因不是 horizon，而是代理几何集合不完整。

### 2. 代理运动学与真实控制器轨迹不一致

当前代理使用

\[
p_{t,k}=p_k^0+\sum_{\ell\le t}B_k a_\ell^{pose},
\]

其中 \(B_k\) 是当前状态附近的固定局部有限差分 Jacobian。它没有表示：

- 控制器内部状态；
- 非线性机器人运动学；
- 动力学与接触响应；
- action clipping；
- 跨决策状态变化；
- 控制器跟踪误差。

如果 first contact 是 robot–yellow_book，而代理仍给出 177 mm，那么应优先怀疑 action mapping 或固定 Jacobian 轨迹误差。

### 3. 认证结果没有真正控制执行许可

按当前方法，每个候选应该在执行前运行 \(C_2\)。如果 step 19 位于当次执行的两步中：

- \(C_2\) 返回 FAIL，但 nominal 仍被执行：gating integration bug；
- \(C_2\) 返回 PASS，而同状态同动作真实执行碰撞：state restore 或 certifier bug；
- \(C_2\) 没有被调用：你实现的是 proxy-only PNSG，不是当前契约中的 `S_wide ∧ C_2`。

`n_repairs=0` 本身不代表系统不需要认证。即使 \(\Delta z=0\)，nominal 也必须经过 \(C_2\)。

### 4. 障碍几何表示错误

“yellow book 只有一个障碍球”值得警惕。书本是薄长方体，单球可能极度改变局部几何：

- 大球通常过于保守；
- 小球可能漏掉书本边角；
- 球心、半径或世界坐标更新错误，也会产生虚假的大净空。

需要将代理球与实际 MuJoCo geom 的 AABB、`geom_rbound` 和 `mj_geomDistance` 做同状态对照。

## 还有一个实现口径问题

冻结的 `selected_constraints()` 会先加入最近的一条约束，然后才根据 margin 停止。因此正常情况下不应真的出现 `constraint_count=0`。

请区分：

```text
constraint_count = 0       # 代理没有生成任何约束，可能是实现问题
violated_constraint_count=0 # 有约束，但所有 b_i<=0，不需要线性修正
repair_count = 0           # 最终没有执行 source steering
```

这三个量不能合并。

## “成功但碰撞”不等于碰撞无害

`success=True` 只能说明任务完成，不能说明安全事件无害。CAR 与 TSR 解耦正是安全研究存在的原因。

如果 yellow book 被撞飞 1.2 m，那么按当前 SafeLIBERO 的禁止接触定义，它仍是安全失败。只有在实验开始前明确规定该物体允许接触，才能不干预；不能因为事后任务成功，就把碰撞重新解释成可接受。

而且

\[
E_{\rm acc}=C_2\land P_H
\]

的含义是“候选既安全又有进度”，不是“只要有进度就允许碰撞”。\(P_H\) 不能覆盖或豁免 \(C_2\)。

## 现在最该做的单状态审计

暂停批量评测，只重跑 `task3 ep44`，对碰撞前后约 4 次决策记录下表：

| 字段 | 要求 |
|---|---|
| decision/query | 对应的真实 action step |
| saved state hash | 保证 proxy、Cert、执行来自同一状态 |
| nominal 10-step actions | clipping 前后均保存 |
| proxy clearance | 每个时刻、每种碰撞主体分别保存 |
| nearest proxy pair | point/primitive/body |
| \(S_{\rm fast}\)、\(S_{\rm wide}\) | 分开记录 |
| \(C_2\) | PASS/FAIL、全部 coverage flags |
| first native contact | geom/body pair 和 simulator substep |
| native minimum distance | robot–obstacle 与 target–obstacle 分开 |
| executed action indices | 明确到底执行 chunk 中哪两步 |
| obstacle displacement | 执行前后 |
| target grasp state | 是否处于附着状态 |

重点检查决策点 `q≈8,9,10`。

## 判因规则

```text
first contact = target–obstacle
→ 代理遗漏抓取物体；补 target geometry。

first contact = robot–obstacle，C2=FAIL，但仍执行
→ 执行门控接线错误。

first contact = robot–obstacle，C2=PASS，复现执行却碰撞
→ certifier/state restore/substep coverage 错误。

C2 正确预警，但 S_wide 大净空
→ 几何代理或 action mapping 错误。

每个碰撞前决策的预测窗口都不包含碰撞动作
→ 才能认定为真正的 horizon 问题。
```

## 我建议的方向

先不要在“纯避障”与“安全且成功”之间选边，也不要立刻扩展预测 horizon。正确顺序是：

1. 固化当前 steering 机制验证：Jacobian、QP、重新前向和净空改善。
2. 把 `ep44` 定义为 proxy–Cert–execution 对齐反例。
3. 精确定位 first contact pair 和最后一次碰撞前认证。
4. 修正遗漏的几何主体、动作映射或门控接线。
5. 若这些都正确，仍确认是长期闭环累积风险，再引入：
   - receding-horizon terminal safety condition；
   - backup invariant set；
   - 多次重规划的风险预测；
   - 或跨 chunk rollout。
6. \(P_H\) 只用于候选效用/进度，不用于放宽安全条件。

当前最强、最诚实的结论不是“PNSG 的单 chunk 方法根本失效”，而是：

> 源空间 steering 技术链已经可运行，但在一个真实危险 episode 上未产生干预；现有证据表明 proxy、非线性认证与实际执行之间至少有一处未对齐。该反例必须完成接触主体和决策时序归因后，才能判断是几何遗漏、认证接线错误、局部模型误差，还是预测 horizon 不足。
