## 两条口径修正

### 1. `1595 / 897 / 84` 不能直接解释为机制占比

这些是 substep contact records。同一次持续接触可能被重复记录几十次，因此只能说明三种机制都出现了，不能据此声称 distractor 机制占多少 episode 或碰撞事件。

至少需要同时报告：

```text
raw contact records
contact-positive control steps
contiguous contact events
contact-positive episodes
unique geom pairs
contact duration substeps
```

真正的机制占比应以独立 episode 或连续 contact event 为单位。

### 2. 1.5% 目前只适用于 task0 单轨迹

正确表述是：

> 在已审计的 task0 nominal trajectory 中，step-end 相对于 any-substep 的 control-step 漏检率为 1/67。

不能先固化成整个 SafeLIBERO 或三种方法的全局漏检率。Step 4 才会回答它是否具有普遍性。

## 角色清单验收门

建议将这次 review 定义为：

```text
ROLE_MANIFEST_GATE
```

只有 PASS 后才开始 Step 4。

### A. 不再依赖正则截取 goal

你已经连续修了三类 regex bug，说明复杂 `And` 和 region 表达式对正则方案过于脆弱。建议把 BDDL goal 解析为完整 S-expression AST：

```text
(And
  (On a b)
  (On c d)
)
```

解析结果应保留为：

```json
{
  "predicate": "And",
  "children": [
    {"predicate": "On", "arguments": ["a", "b"]},
    {"predicate": "On", "arguments": ["c", "d"]}
  ]
}
```

角色推导应基于 AST，不再基于字符串切片。

### B. 每条 goal clause 单独保存证据

每个角色记录必须能回溯到具体 goal：

```json
{
  "object": "akita_black_bowl_1",
  "roles": ["MANIPULATED_TARGET"],
  "evidence": [{
    "predicate": "On",
    "argument_position": 0,
    "goal_clause": "(On akita_black_bowl_1 plate_1)"
  }]
}
```

```json
{
  "object": "plate_1",
  "roles": ["GOAL_RECEPTACLE"],
  "evidence": [{
    "predicate": "On",
    "argument_position": 1,
    "goal_clause": "(On akita_black_bowl_1 plate_1)"
  }]
}
```

对象角色最好允许为集合，而不是单字符串。复杂任务中同一物体可能在不同 goal clause 中承担多个语义角色。

### C. region 必须解析到父对象

对：

```text
table_region
plate_region
basket_inside_region
```

需要区分：

- region 属于某个 object；
- region 属于 workspace/table；
- region 是纯逻辑区域；
- region 无法静态解析。

不能把所有 region 都标为 `GOAL_RECEPTACLE`。应保留：

```text
region_name
region_parent
region_parent_role
resolution_status
```

### D. 谓词到角色的规则显式版本化

至少检查这些类型：

| Goal predicate | 典型角色规则 |
|---|---|
| `On(a,b)` | `a` 为 manipulated target，`b` 为 goal/support |
| `In(a,b)` / `Inside(a,b)` | `a` 为 target，`b` 为 receptacle |
| `Open(a)` / `Close(a)` | `a` 为 manipulated task object，但不一定是 payload |
| `TurnOn(a)` / `TurnOff(a)` | `a` 为 task-controlled object |
| 多重 `And` | 所有子句取并集 |
| region argument | 先解析父对象，再推导角色 |

不要把所有 goal 第一个参数一律视为可携带 payload。对打开、关闭、旋转等任务，需要单独角色，例如：

```text
TASK_CONTROLLED_OBJECT
```

### E. 角色完整性断言

对全部 17 个任务运行：

```text
所有 goal predicate 均被解析
所有 goal argument 均能解析到 object 或 region
所有 declared movable object 均获得角色
所有 static safety obstacles 均来自安全障碍注册表
不存在未解释的 UNKNOWN object
不存在 distractor 与 manipulated target 的无证据冲突
geom IDs 不交叉归属到两个物理实例
BDDL SHA-256 已保存
role manifest SHA-256 已保存
```

允许对象具有多角色，但必须有明确证据和接触分类优先级。

### F. 17 个任务全部人工复核

建议生成一张紧凑表：

| Task | Goal clauses | Manipulated | Goal/receptacle | Controlled | Distractors | Obstacles | Unresolved |
|---|---|---|---|---|---|---|---|

17 行可以全部人工检查，不需要抽样。

尤其检查：

- 多重 `And`；
- 两个以上 manipulated objects；
- region 作为目标；
- 容器同时出现在 goal 中；
- open/close/turn-on 类型任务；
- 同一 object 出现在多个 goal clause；
- obstacle 名称同时出现在普通 object declarations。

## ContactEventRecorder 也应做一处调整

允许接触不要直接丢弃，应该保留为独立类别：

```text
allowed_robot_target
allowed_target_goal
```

它们不进入 forbidden-contact 指标，但保留记录有两个好处：

1. 可以检查阶段规则是否正确；
2. 可以发现本应 forbidden 的 contact 被错误地归入 allowed。

建议六类扩展为：

```text
robot_obstacle
payload_obstacle
robot_distractor
distractor_obstacle
allowed_robot_target
allowed_target_goal
other_unclassified
```

`other_unclassified` 必须为零或逐项解释。

## ROLE_MANIFEST_GATE 判定

```text
PASS:
  17/17 tasks reviewed
  unresolved goal arguments = 0
  unclassified relevant geoms = 0
  complex And tests pass
  region-parent tests pass
  task0 expected roles pass
  hashes and evidence paths complete

UNKNOWN:
  存在动态 region、未知 predicate 或无法绑定的 object

FAIL:
  已知对象被错误归类，或 parser 丢失 goal clause
```

## Gate 通过后立即启动 Step 4

Step 4 的目标不是生成新 CAR，而是分解：

\[
CAR_{\rm benchmark\ trigger}
\longrightarrow
\{\text{robot, payload, distractor, instability, unknown}\}.
\]

每个 episode 使用多标签，而不是强制互斥。一个 episode 可以同时出现：

```text
robot-obstacle
robot-distractor
distractor-obstacle
```

因此各机制比例之和可以超过 100%。

主统计单位使用 episode：

```text
P(robot contact | official CAR failure)
P(payload contact | official CAR failure)
P(distractor disturbance | official CAR failure)
P(scene instability | official CAR failure)
P(no identified contact | official CAR failure)
```

同时报告“首次超过官方 1 mm 阈值之前已经出现的机制”，因为这比整条 episode 的任意共现更接近 CAR 触发来源。

## 最终建议

执行顺序冻结为：

```text
1. 完整 review 17-task role manifest
2. ROLE_MANIFEST_GATE=PASS
3. 冻结 contact classification contract 和 manifest hash
4. task0 重新汇总为 episode/event/control-step 三个单位
5. 启动三方法分层 CAR source decomposition
6. 从确认的真实 robot-obstacle 状态选择 PNSG 正对照
7. 运行 PNSG 单状态配对 smoke
```

所以现在先做角色清单 review。这个 review 是一次性的，而且成本远低于在错误标签下重跑整个 Step 4。
